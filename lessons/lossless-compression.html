Shrinking files without losing a bit

Files get smaller when a computer spots patterns and writes them down more cleverly. In this lesson you’ll compress text, pictures, and raw bits yourself, then unpack them to prove nothing was lost.

Your work saves in this browser as you go. At the end you’ll download a PDF recap of everything you did and upload it to Canvas.

1

Why compress?

Computers can store huge numbers of files, but size still matters. Smaller files take less storage and travel faster over a network. A compression algorithm reduces the number of bits needed to represent a file.

There are two kinds. Lossless compression shrinks a file without losing any information, so the original can be rebuilt exactly. Lossy compression throws away less important details to save even more space, so the original can’t be rebuilt perfectly.

You already compress text

People shorten text messages all the time. Translate each one back into full text.

Lossless or lossy?

Lossless

Shrinks the file without losing anything. When you unpack it, you get back the exact original, bit for bit.

Lossy

Shrinks the file more by throwing away details people probably won’t notice. You can’t get the exact original back.

For each file, ask: would losing a tiny bit of detail cause a problem? If yes, it must be lossless. If no one would notice, lossy is OK.

Key idea

Lossless compression rebuilds the original exactly; lossy compression trades away some detail for a smaller file. Anything where every bit matters, like text, code, or numbers, needs lossless.

2

Compressing text

Computers compress text the way you shorten messages, except they never guess. They find repeated sequences and replace each one with a single symbol that isn’t in the text. A dictionary records what each symbol stands for, so the computer can put everything back.

For example, in to be or not to be, that is the question, replacing “to” with ☀ and “be” with ☂ gives ☀ ☂ or not ☀ ☂, that is the question.

Your turn: type a repeated sequence into the dictionary box and press Enter. Watch the sizes change. The compressed file is the compressed text plus the dictionary, so a pattern only helps if it saves more than it costs.

Compressed text

Dictionary

    Each dictionary entry costs its symbol plus its pattern (pattern length + 1 characters).

    You can also try the same idea in Code.org’s Text Compression Widget (Unit 1, Lesson 9): open it in a new tab after logging in to Code.org. Its numbers can differ slightly from this page’s because it counts dictionary size its own way.

    Key idea

    Text compression replaces repeated sequences with short symbols and stores a dictionary to undo it. More repetition means more compression. Text with no repeats, like the alphabet, can’t be compressed and can even get bigger.

    Images and run-length encoding

    A picture with just two colors can be stored as a bitmap: each pixel becomes one bit. In this 16 × 16 heart, white pixels are 0 and purple pixels are 1, so the uncompressed image is 256 bits.

    
      
    
    
    
    
    Imagine reading those bits aloud. You’d soon say “five zeros” instead of “zero zero zero zero zero.” Run-length encoding (RLE) does exactly that. Each row becomes a list of run lengths, always starting with the number of white pixels.
    
    
    Row 1 is 0001100000110000: 3 white, 2 purple, 5 white, 2 purple, 4 white. In RLE that’s 3,2,5,2,4.

    Key idea
    RLE replaces runs of the same color with counts. It works great on simple images with long runs, and works better as those runs get longer. Photos have so many slightly different colors that RLE barely helps. Fax machines still use it for black-and-white pages.
    
  
    

  
  
    
    
    4
    Huffman coding
    
    
    Every file is ultimately a sequence of bits, so some compression works on any kind of file. Huffman coding gives shorter codes to common symbols and longer codes to rare ones.
    
    
    DNA uses only four letters: a, c, g, and t. An E. coli DNA sequence, 4.6 million letters long, starts with agcttttcattct. With four letters, a computer would normally use 2 bits for each:
    
    
    a = 00c = 01g = 10t = 11
    
    
    
    
    But “t” appears 7 times, “c” 3 times, “a” twice, and “g” just once. Give “t” the shortest code and the total drops:
    
    
    t = 1c = 00a = 010g = 011
    
    
    Now the 13 letters take only 22 bits. That may not sound like much, but over 4.6 million letters it adds up.
    
    
    
    
    

    
    Huffman builder
    
    
    Type any text. The builder counts each character, joins the two rarest into a tree again and again, then reads each character’s code from the path to it: left is 0, right is 1. When two branches tie, codes of the same length can swap places, so your codes may not match the example above exactly, but the total number of bits is the same.

    Key idea
    Huffman coding gives frequent symbols short codes and rare symbols long ones. No code is the start of another, so the bits decode in exactly one way. PNG images and ZIP files combine a repeated-sequence method like the text example with Huffman coding.
