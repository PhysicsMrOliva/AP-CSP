How this guide works

  1. Open your starter code in CMU CS Academy. Each function already has its header, comments, and the word pass as a placeholder.

  2. Pick a step below. Read what the function does and why it exists, then reveal the code one chunk at a time. Type each chunk into your function in place of pass, then delete pass. CMU doesn't let you paste into your program, so you'll type every line, which also helps you notice what each one does.

  3. Test before moving on. Type the test code at the very bottom of your program, exactly as shown. Write your prediction, run the program, then paste what the console actually printed into this page. Compare the two. Everything you type is saved in your Testing Log at the bottom of this page. At the end of each class, download the log as a PDF and upload it to Canvas to show your progress.

  4. Put a # in front of each test line so it stops running (that's called "commenting it out"), check the step off, and go to the next function.

Where does test code go? Python reads your program from top to bottom. A function has to be defined before a line that calls it runs, so tests always go after all the def blocks:

import random
# Variable Declarations     colors, dice shapes, buttons, app.diceCount
# FUNCTION DEFINITIONS      def rollDice ... def onMousePress
# TESTS (temporary)         type test code down here, at the very bottom

You'll jump around your file a bit: the steps go in a different order than the functions appear in the starter code. Use Ctrl+F (Cmd+F on a Mac) to find each def.

Why break a project into functions?

You could write this whole app as one giant block of code inside onMousePress. It would work, but it would be about four times longer and much harder to fix. Here's what small functions buy you, with real examples from this project:

Easier to read

onMousePress reads like a to-do list: "if Roll was clicked, rollAllDice()." You can tell what happens without reading the details.

Easier to debug

You can test rollDice(6) by itself before a single button works. If the total is wrong, there's exactly one place to look: totalDice().

Easier to reuse

rollDice() is written once and called from 4 places: three times in rollAllDice() and once in updateDice().

Easier to maintain

If Google changes its purple, you change one line in getDiceColor(), and every purple die updates.

More collaborative

One partner can write getDiceColor() while the other writes addDice(). They only need to agree on the function's name, its parameters, and what it returns.

Four ideas you'll use in every step

Parameters and return values

Parameters are a function's inputs. The return value is its output.

6→rollDice(numSides)→4

In rollDice(6), 6 is the argument and numSides is the parameter that receives it. Some functions don't return anything. Instead they change the canvas, like totalDice().

Helper functions

Small functions that do one job for bigger functions.

updateDiceusesgetDiceColorrollDicetotalDice

Build the helpers first, test them, then trust them when you build the big functions.

Global variables with app.

Values that every function needs to share, like app.diceCount, are stored on the app object.

If you wrote diceCount += 1 inside a function, Python would treat diceCount as a brand-new local variable and crash. app.diceCount belongs to the app, so any function can read it and change it. Shapes like leftDice are global too, so functions can change their properties.

DRY: Don't Repeat Yourself

If you're copying and pasting code, you probably need a function, or a parameter.

updateDice() works on the left, middle and right die because the die is a parameter. Without that, you'd paste the same 20 lines three times, and fixing a bug would mean fixing it three times.
